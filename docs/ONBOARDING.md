# Заведение клиента — рунбук на 15 минут

Путь от «клиент оплатил» до «владелец залогинился и видит свой пустой стол».
Читает оператор платформы. Инструкция для самого подрядчика лежит рядом —
[OWNER-GUIDE.md](OWNER-GUIDE.md), её отдают в конце.

| Шаг | Что делаем | Время |
|---|---|---|
| 1 | Поддомен | 2 мин |
| 2 | Проверка окружения | 1 мин |
| 3 | `provision-tenant` | 2 мин |
| 4 | Передача доступов | 2 мин |
| 5 | Первый вход владельца | 2 мин |
| 6 | Канал лидов | 4 мин |
| 7 | Контрольный лид | 2 мин |

---

## Шаг 0 — что должно быть готово один раз

Это делается при развёртывании платформы и дальше повторяется только при переезде.

- Приложение поднято по [../DEPLOY.md](../DEPLOY.md), `.env` заполнен по `.env.example`.
- Рабочая база — `dev.db` в корне репозитория. Файл `prisma/dev.db` устаревший, там нет
  даже таблицы `Tenant`; проверяйте, что `DATABASE_URL` смотрит на корневой.
- Бэкапы включены и проверены восстановлением (`scripts/backup.sh`, `scripts/restore.sh`).
  Первый клиент заводится после того, как восстановление проверено хотя бы раз.
- Есть платформенный воркспейс — ваш собственный, из которого работает супер-админка
  `/admin`. Как его завести, см. шаг 2.

## Шаг 1 — поддомен

Каждая контора живёт на своём поддомене третьего уровня: `korvex.crm.example.ca`.
Воркспейс читается из первой метки хоста (`src/lib/tenant-slug.ts`), при этом `www`
пропускается, а голый апекс отдаёт слаг `demo`. Отсюда правило: у клиента должен быть
именно поддомен, иначе он попадёт в чужой воркспейс и получит `403`.

1. Wildcard-запись `*.crm.example.ca` → IP сервера (или CNAME на прокси).
2. Wildcard-сертификат на `*.crm.example.ca`.
3. Проверка: `curl -I https://<slug>.crm.example.ca/login` отдаёт `200`.

Слаг придумывайте коротким и связанным с названием: `korvex`, `beavermovers`.
Латиница, цифры и дефис внутри, 2–40 символов. Скрипт откажет на `www`, `api`, `app`,
`admin`, `mail`, `smtp`, `static`, `assets`, `login`, `register`, `expired`, `demo`,
`test`, `staging` — они принадлежат платформе.

## Шаг 2 — проверка окружения

| Переменная | Зачем при заведении клиента |
|---|---|
| `DATABASE_URL` | корневой `dev.db`, тот же, что видит приложение |
| `NEXTAUTH_URL`, `NEXTAUTH_SECRET` | вход и внутренний вызов `/api/tenant/resolve` |
| `SUPER_ADMIN_EMAILS` | адреса операторов платформы |
| `PLATFORM_TENANT_SLUG` | слаг вашего воркспейса; пустое значение выключает `/admin` целиком |
| `TRIAL_DAYS` | срок самостоятельной регистрации с сайта |
| `LEAD_DEDUP_DAYS` | окно, внутри которого повторная заявка с того же адреса считается той же |
| `MAILGUN_WEBHOOK_SIGNING_KEY`, `SMTP_*` | почтовый канал лидов и письма-напоминания |

Супер-админом становится админ, у которого адрес есть в `SUPER_ADMIN_EMAILS` **и**
чей аккаунт лежит в воркспейсе `PLATFORM_TENANT_SLUG`. Оба условия обязательны.

Платформенный воркспейс заводится тем же скриптом (единственное место, где операторский
адрес разрешён — в клиентском воркспейсе скрипт его отклонит):

```bash
cd /data/projects/Crmhandyman
npx ts-node --compiler-options '{"module":"CommonJS"}' scripts/provision-tenant.ts \
  --business "MMIX Platform" --slug mmix --owner ops@mmix.ca --plan paid \
  --domain crm.example.ca
```

После этого `PLATFORM_TENANT_SLUG=mmix` в `.env` и перезапуск приложения.

## Шаг 3 — provision-tenant

```bash
cd /data/projects/Crmhandyman
npx ts-node --compiler-options '{"module":"CommonJS"}' scripts/provision-tenant.ts \
  --business "Korvex Developments" \
  --slug korvex \
  --owner vlad@korvex.ca \
  --owner-name "Vlad" \
  --plan paid \
  --worker "Ivan Petrov <ivan@korvex.ca>" \
  --worker dana@korvex.ca \
  --domain crm.example.ca
```

Запускать из корня репозитория: `DATABASE_URL` содержит относительный путь, и из другого
каталога скрипт откроет пустую базу рядом с собой. `npx tsx scripts/provision-tenant.ts`
работает так же, если tsx установлен глобально.

| Аргумент | Смысл |
|---|---|
| `--business` | название конторы, видно в шапке и в документах |
| `--slug` | поддомен и адрес воркспейса |
| `--owner` | почта владельца, становится его логином и ролью ADMIN |
| `--owner-name` | имя человека в журнале; по умолчанию берётся название конторы |
| `--plan paid\|demo` | по умолчанию `paid`, у него нет срока |
| `--trial-days` | срок для `demo`, по умолчанию 14 |
| `--worker` | повторяемый: `"Имя <почта>"` или голый адрес |
| `--domain` | база для печати адреса входа |
| `--owner-password-stdin` | взять пароль владельца со stdin |
| `--add-workers` | доукомплектовать существующий воркспейс |
| `--reset-password <email>` | выдать новый пароль одному аккаунту |

Что скрипт гарантирует:

- **Пустой стол.** Демо-лиды, демо-счета и демо-работник сеются только при регистрации
  с сайта. Платящий клиент открывает чистую CRM.
- **Пароли только в выводе.** Аргументы командной строки видны в `ps` и в истории
  оболочки, поэтому паролей там нет: скрипт генерирует по 20 случайных символов на
  человека и печатает их один раз. Свой пароль владельца отдают через stdin:
  `... --owner-password-stdin < /run/secrets/vlad.txt` (такой пароль обратно на экран
  уже не выводится).
- **Идемпотентность по слагу.** Повторный запуск с тем же слагом сообщает, чей это
  воркспейс, и ничего не меняет. Второго тенанта на том же адресе не появится.
- **Проверки до записи.** Формат слага, занятость слага, корректность адресов,
  дубликаты работников — всё проверяется до первого обращения к базе, и список ошибок
  печатается целиком.

Коды возврата: `0` — сделано или уже было сделано, `2` — аргументы, `3` — сбой базы.

Первая строка журнала воркспейса пишется тут же: `tenant.provision`. Владелец увидит её
в Настройки → Журнал.

## Шаг 4 — передача доступов

Блок с паролями показывается один раз, в базе лежат только хэши. Отдавайте по одному
человеку в личку, минуя общие чаты, и просите сменить пароль в первый же день.

Пароль потерян — выдаётся новый:

```bash
npx ts-node --compiler-options '{"module":"CommonJS"}' scripts/provision-tenant.ts \
  --slug korvex --reset-password vlad@korvex.ca --domain crm.example.ca
```

Старый пароль после этого перестаёт работать. Это же лечение, когда телефон с открытой
сессией уехал вместе с уволившимся техником.

Новый работник появился позже:

```bash
npx ts-node --compiler-options '{"module":"CommonJS"}' scripts/provision-tenant.ts \
  --business "Korvex Developments" --slug korvex --owner vlad@korvex.ca --add-workers \
  --worker "Roman <roman@korvex.ca>" --domain crm.example.ca
```

Уже заведённые аккаунты такой запуск пропускает, их пароли остаются прежними. Владелец
умеет то же самое сам: Настройки → Команда.

## Шаг 5 — первый вход владельца

1. Открыть `https://<slug>.crm.example.ca/login`.
2. Войти почтой и паролем из шага 3.
3. Убедиться, что стол пустой: 0 лидов, 0 работ, 0 счетов.
4. Проверить роли: у владельца открыты «Финансы» и «Счета», работник с тех же страниц
   уезжает на `/today`.

Клиент заходит только со своего поддомена. Сессия привязана к воркспейсу, и на чужом
адресе middleware отдаст `403` — так закрыт обход платного гейта.

## Шаг 6 — канал лидов

Квизы-лендинги (`beavermovers-quiz`, `korvex-quiz`) уже шлют JSON вида
`{name, phone, email, ...ответы}` в свой `send_lead.php`. Задача — добавить туда второй
адресат, наш приёмник.

1. Владелец (или вы под его аккаунтом) открывает Настройки → Приём лидов.
2. Создаёт ключ: подпись (например «Korvex quiz») и источник, которым пометятся лиды.
3. Копирует адрес `https://<slug>.crm.example.ca/api/intake/<ключ>` — он показывается
   один раз, дальше хранится только хэш.
4. Ключ вписывается в `send_lead.php` лендинга.

Формат тела, сопоставление полей квиза с полями лида, отзыв ключа и разбор ошибок —
в [INTAKE.md](INTAKE.md).

Почтовые лиды (HomeStars, Kijiji) идут другим путём: Настройки → Интеграции, канал EMAIL
с адресом получателя. Маршрутизация по адресу обязательна, иначе лиды уедут в тот
воркспейс, который завёл канал первым.

## Шаг 7 — контрольный лид

```bash
curl -sS -X POST https://<slug>.crm.example.ca/api/intake/<ключ> \
  -H 'Content-Type: application/json' \
  -d '{"name":"Проверка канала","phone":"613-555-0100","email":"check@example.com","message":"onboarding test"}'
```

Приёмка:

- ответ `{"ok":true,...}`;
- лид виден в `/leads` с нужным источником;
- в Настройки → Приём лидов у ключа обновилась колонка последнего использования;
- тестовый лид отклонён или удалён, чтобы не мешал в первый рабочий день.

Затем прогоняется настоящая отправка формы с самого лендинга — один клик по кнопке
квиза. Проверка через `curl` показывает, что жив приёмник; отправка с лендинга
показывает, что жив весь путь.

## Шаг 8 — передача клиенту

Отправьте владельцу три вещи: адрес входа, его логин и [OWNER-GUIDE.md](OWNER-GUIDE.md).
Через день загляните в Настройки → Журнал его воркспейса: живые строки о лидах и сметах
означают, что человек начал работать.

## Чек-лист приёмки

- [ ] поддомен отвечает по HTTPS
- [ ] воркспейс создан, слаг совпадает с поддоменом
- [ ] план `PAID`, срок не выставлен
- [ ] стол пустой: 0 лидов, 0 работ, 0 счетов
- [ ] владелец вошёл и сменил пароль
- [ ] работник вошёл, «Финансы» ему закрыты
- [ ] ключ приёма лидов выпущен и вписан в лендинг
- [ ] контрольный лид дошёл и убран
- [ ] бэкап базы снят после заведения клиента

## Что ломается чаще всего

| Симптом | Причина | Лечение |
|---|---|---|
| `403` на всех страницах после входа | адрес в браузере принадлежит другому воркспейсу | заходить на свой поддомен |
| Редирект на `/register` | слаг из адреса в базе отсутствует | опечатка в поддомене или в `--slug` |
| Экран `/expired` | план `DEMO` и срок вышел | перевести на `PAID` в `/admin` |
| `/admin` отдаёт `401` вашему аккаунту | адрес есть в `SUPER_ADMIN_EMAILS`, аккаунт лежит вне платформенного воркспейса | завести аккаунт в воркспейсе `PLATFORM_TENANT_SLUG` |
| Лид не дошёл, приёмник отвечает `404` | ключ отозван, удалён или скопирован с ошибкой | выпустить новый ключ |
| Приёмник отвечает `429` | сработал троттлинг: 10 отправок с одного IP за 10 минут, 60 на ключ в час | подождать окно |
| Повторная заявка «пропала» | тот же адрес внутри окна `LEAD_DEDUP_DAYS` | так задумано; окно меняется переменной |
| Работник жалуется на скрытые «Финансы» | роль WORKER закрывает книгу и экспорт | так задумано, см. OWNER-GUIDE |
| Вход владельца отклонён после сброса | у человека сохранён старый пароль | выдать пароль ещё раз через `--reset-password` |
